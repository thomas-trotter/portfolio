I could have had a portfolio online in an afternoon with a template. Instead I spent considerably longer building this site from scratch with Next.js, TypeScript, and Tailwind CSS — and I think that was the right call. A portfolio is supposed to be evidence of how you work, and a template proves nothing. This post is a short tour of how the site is put together and the decisions behind it.

## Why build it from scratch

The honest answer is that the site itself is the project. Every choice on it — the routing, the styling system, the content pipeline, the contact form — is a decision I made and can defend, which is exactly what I want a portfolio to demonstrate. It was also a deliberate excuse to properly learn the modern Next.js App Router world: server components by default, static generation from data, and React Server Actions instead of hand-rolled API routes.

## Content as data

The decision I'm happiest with is keeping every piece of content — project pages, blog posts (including this one), the about page — out of the components entirely. Each one is an MDX file in a `content/` folder, and a tool called [Velite](https://velite.js.org) validates them against a schema at build time and generates TypeScript types for the rest of the app to consume.

That buys two things. First, safety: if I typo a frontmatter field or forget a required one, the build fails loudly instead of a page shipping half-broken. Second, leverage: slugs, permalinks, excerpts, and read times are all computed in schema transforms, so publishing a new project means writing one file and everything else — the cards, the detail page, the SEO metadata, the static routes — picks it up automatically.

## Small components, boring styling

The UI is built from a handful of small primitives — cards, tags, pills, sections, form fields — rather than page-sized components, and styled with Tailwind CSS using a small set of design tokens defined in `oklch`. Keeping every colour and spacing decision in one place made it much easier to iterate on the look without the design slowly drifting apart from page to page.

## A contact form without a backend

The contact form was a nice excuse to use React Server Actions properly. Submissions run through a Zod schema on the server with per-field error messages, a hidden honeypot field quietly swallows bot submissions while pretending to succeed, and delivery happens through the Resend API. There's no client-side form library and no separate backend service — just a validated server function.

## What I learned

The biggest lesson was that "treat it like production software" is a habit, not a feature: type-checking the content, linting, working through pull requests, and writing things down all paid for themselves within weeks. It's the same philosophy behind my [Image Processing API](/projects/image-processing-api) — shipping something properly, not just making it work.
